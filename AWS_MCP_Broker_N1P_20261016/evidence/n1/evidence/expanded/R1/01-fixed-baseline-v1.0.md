## 5. 機能要件

### 5.1 AWSアカウント管理

**REQ-001 — 明示的なアカウント登録**

アクセス可能なAWSアカウントは管理者が明示的に登録する。

未登録アカウントへのアクセスは禁止する。

**REQ-002 — 利用者・エージェント別のアクセス制御**

管理者は利用者・AIエージェントごとにアクセス可能なAWSアカウントを設定できること。

**REQ-003 — タスク単位の対象アカウント指定**

調査タスクには対象アカウントを1つまたは複数指定できること。

タスク中は指定された範囲内でアカウントを切り替えられること。

タスク指定によって既存のアクセス権限が拡大してはならない。

**REQ-004 — 操作ごとの認可**

すべてのAWS API操作について、利用者、エージェント、タスク、対象アカウント、対象リソース、操作を検証すること。

認可取消が有効になった後、新しいAPI操作を許可してはならない。

認可状態が不明な場合は拒否する。

### 5.2 認証・一時クレデンシャル

**REQ-005 — 読み取り専用をデフォルトとする**

アクセスモードの指定がない場合は読み取り専用とする。

読み取り調査のために書き込み権限を自動取得してはならない。

**REQ-006 — 読み取り用一時クレデンシャル**

読み取り用クレデンシャルの有効期限は原則1時間とする。

調査が継続中の場合、認可を再検証したうえで自動的に新しいクレデンシャルを取得できること。

**REQ-007 — AWS長期アクセスキーの禁止**

AWSへの初期認証は鍵なしワークロード認証を必須とする。

長期AWSアクセスキーを使用してはならない。

**REQ-008 — 無人運用**

AWS認証情報の取得・更新に定期的な人間のログインを要求しないこと。

Deno Deploy、Cloudflare Workers、Dockerのすべてでこの要件を満たすこと。

**REQ-009 — 認証情報の非公開**

AWS認証情報、一時クレデンシャル、Bitwarden認証情報をAIエージェント、MCP応答、通常ログへ公開してはならない。

認証情報はBrokerの保護された実行境界でのみ使用すること。

### 5.3 利用者・エージェント認証

**REQ-010 — 対話型認証**

対話型利用では、利用者とAIエージェントの両方を検証すること。

**REQ-011 — 無人型認証**

無人実行では、登録済みサービス主体とAIエージェントを検証し、責任者を追跡できること。

**REQ-012 — Portalと直接接続**

Cloudflare MCP Portal経由とMCPクライアントからの直接接続の両方をサポートすること。

接続経路によって認可保証が変化してはならない。

**REQ-013 — Portal経由の本人性検証**

Portalが検証可能な利用者・エージェント識別情報を引き継げない場合、Broker側で独立した認証を要求すること。

認証結果と対象リクエストを安全に紐づけられない場合は拒否すること。

共有Bearer Tokenや自己申告の利用者IDだけを本人確認として扱ってはならない。

### 5.4 書き込み操作

**REQ-014 — 個別の人間承認**

書き込み操作は、1操作ごとに人間の承認を必須とする。

**REQ-015 — 独立したWeb承認**

書き込み承認は、AIエージェントから独立したWeb画面で本人確認後に実施すること。

エージェント自身による承認の偽装を許してはならない。

**REQ-016 — 承認内容の固定**

承認には、対象アカウント、リソース、操作、パラメータ、承認主体、有効期限を紐づけること。

承認後にこれらの内容を無断変更してはならない。

**REQ-017 — 承認の一回限りの利用**

1つの承認で実行できる書き込み操作は1回だけとする。

並行実行、再送、障害復旧、バックアップ復元後も、同じ承認を再利用できてはならない。

**REQ-018 — 承認期限**

- 承認待ち：15分
- 承認後の実行開始期限：5分

拒否・期限切れ・取消時は実行を禁止する。

**REQ-019 — 書き込み操作の許可リスト**

初期リリースでは、管理者が登録した検証済み書き込み操作のみを許可する。

対象リソース、パラメータ、必要権限を安全に制限できない操作は拒否する。

**REQ-020 — 書き込みの自動再試行禁止**

通信断・タイムアウトなどで結果が不明な場合、同じ書き込みを自動再実行してはならない。

読み取り操作で状態を確認し、結果を確定できなければ `outcome_unknown` を返す。

追加の書き込みには新しい承認を必要とする。

**REQ-021 — 高リスク操作の禁止**

初期リリースでは以下を禁止する。

- IAMのユーザー・ロール・権限設定の変更
- 認証情報の作成・変更
- AWSアカウント・Organizationsの管理変更
- セキュリティ機能の無効化
- 監査機能・監査ログの改変
- Broker自身の認可・承認・認証基盤への変更
- 上記を間接的に実行する迂回操作

人間が承認しても禁止事項は解除されない。

### 5.5 読み取り・調査機能

**REQ-022 — AWS全般への対応**

初期リリースからAWS全般を調査対象とする。

ただし、認可・安全性を検証できた読み取り操作のみ公開する。

未検証のAWS APIを無条件に許可してはならない。

**REQ-023 — 機密情報の制限**

AWSリソースの構成・メタデータ・コスト情報は広く調査できること。

秘密値、機密データ本文、認証情報などは原則取得を禁止する。

例外は管理者による明示的な許可を必要とする。

**REQ-024 — AWS公式MCPとの部分互換**

安全性を維持できるAWS公式MCP機能について、可能な範囲で互換性を提供する。

内部のAWS API呼び出しを個別に認可できない複合操作は拒否するか、安全な独自機能で代替する。

### 5.6 Bitwarden・管理機能

**REQ-025 — Bitwarden Secrets Manager**

Bitwarden Secrets Managerを秘密情報の保管先として利用する。

Bitwardenの初期認証情報は実行環境の保護されたSecrets機能から取得すること。

**REQ-026 — Broker内蔵の設定管理**

次の設定はBroker内部で永続管理する。

- AWSアカウント登録
- 利用者・エージェントのアクセス権限
- 操作許可ポリシー
- API呼び出し制限
- 管理設定

**REQ-027 — 管理者Web画面**

管理者はBroker専用Web画面から設定を登録・変更できること。

管理設定の変更には適切な管理者認証・認可を要求すること。

**REQ-028 — Gitへの設定依存禁止**

運用設定の保管・変更にGitリポジトリを必要としてはならない。

Brokerは独立したシステムとして管理・運用できること。

### 5.7 タスク・利用量管理

**REQ-029 — API利用上限**

タスク・エージェントごとに以下の上限を設定できること。

- AWS API呼び出し回数
- 実行時間
- 推定API利用料金

システム全体にも強制上限を設けること。

複数アカウントを横断した利用量を合算すること。

**REQ-030 — 上限到達時の動作**

上限到達後は新規API操作を禁止すること。

取得済みの結果と未調査項目を区別して返すこと。

**REQ-031 — 読み取りタスクの復旧**

障害後、タスク・認証・認可・保存状態を再検証できた場合のみ、安全な読み取り処理を自動再開できること。

書き込み操作は自動再実行してはならない。

### 5.8 失効・取消・障害時の安全性

**REQ-032 — 終了・取消時の新規操作禁止**

タスク終了、認可取消、承認取消を受け付けた場合、新規API操作と新規認証情報発行を停止すること。

取消と操作開始が競合しても、取消が有効になった後の新規操作を許可してはならない。

**REQ-033 — 実行中操作の扱い**

実行中の操作は可能な範囲で停止する。

AWSが既に受け付けた処理の取消成功は保証しない。

結果不明の場合は `outcome_unknown` とする。

**REQ-034 — 認証情報の残存追跡**

STS認証情報を安全に失効できる場合は失効処理を行う。

即時失効できない場合は、残存状態と期限を追跡すること。

Brokerによる追加操作の禁止と、AWS側での認証情報の失効は別の保証として扱う。

**REQ-035 — Fail Closed**

認証・認可・承認・監査・永続状態など、安全性に必要な条件を確認できない場合、新しい対象操作を拒否すること。

### 5.9 監査・永続化・バックアップ

**REQ-036 — 構造化監査**

利用者、エージェント、対象アカウント、タスク、操作、承認、権限発行、実行結果、失効・残存状態を追跡できる構造化監査ログを記録すること。

**REQ-037 — 監査ログの保護**

- 追記型
- 最低90日間保持
- AIエージェントによる改変・削除禁止
- 秘密情報の記録禁止

**REQ-038 — データ永続化**

設定・認可・承認・タスク・監査状態を永続化すること。

**REQ-039 — 自動バックアップ**

暗号化されたバックアップを自動取得すること。

重大障害時には管理者による復元を許可する。

**REQ-040 — 復元時の安全性**

復元後に状態整合性を確認できない場合はFail Closedとする。

古いバックアップから使用済み承認が復活してはならない。

監査ログの保持義務を復元処理によって損なってはならない。

### 5.10 実行環境

**REQ-041 — 複数実行環境への対応**

以下の3環境をサポートする。

1. Deno Deploy
2. Cloudflare Workers
3. Docker（Linux / macOSホスト）

**REQ-042 — 機能・安全性の同等性**

環境固有の内部実装の違いは許容する。

ただし、利用可能な機能、認可・承認・秘密情報保護・監査・障害復旧の安全性保証を弱めてはならない。

**REQ-043 — Broker単位で独立**

異なるBrokerインストール間では、設定・認可・承認・タスク状態を独立させる。

同一Brokerの複数インスタンスは必要な状態を共有し、承認の二重利用を防止する。

**REQ-044 — AWS Lambda不要**

AWS Lambdaを必須の実行基盤としてはならない。

## 10. 受け入れ基準（原文）

初期リリースでは、次の条件をすべて満たすこと。

| ID | 検証対象 | 合格条件 |
|---|---|---|
| AC-001 | 鍵なし認証 | 3環境で長期AWSアクセスキーなしに認証可能 |
| AC-002 | マルチアカウント | 登録済み複数アカウントを安全に切替可能 |
| AC-003 | アカウント隔離 | 未登録・未認可アカウントにアクセス不可 |
| AC-004 | ReadOnly | 読み取りクレデンシャルで書き込み不可 |
| AC-005 | 自動更新 | 有効期限切れ後も認可済み調査を継続可能 |
| AC-006 | 本人性 | Portal・直接接続の双方で必要な主体を検証 |
| AC-007 | 個別承認 | 有効な人間承認なしに書き込み不可 |
| AC-008 | 承認一回限り | 同時要求・再送・再起動で二重実行しない |
| AC-009 | 承認期限 | 期限切れ・拒否・取消後に書き込み不可 |
| AC-010 | 高リスク操作 | 直接・間接の禁止操作が拒否される |
| AC-011 | 認可取消 | 取消が有効になった後の新規操作を防止 |
| AC-012 | クレデンシャル隔離 | AI・ログ・応答から秘密値を取得できない |
| AC-013 | 書き込み障害 | 結果不明時に自動再実行しない |
| AC-014 | 読み取り復旧 | 安全性の再検証後のみ自動復旧 |
| AC-015 | 利用量制限 | タスク・全体の上限を強制できる |
| AC-016 | 監査 | 必要なイベントを構造化して記録・保護 |
| AC-017 | バックアップ | 復元後も使用済み承認が復活しない |
| AC-018 | 環境互換 | 3環境で同じ安全性の試験を通過 |
| AC-019 | MCP互換 | 実際のMCPツール呼び出しまで認可を強制 |
| AC-020 | 実AWS検証 | 隔離非本番AWS環境で正常系・障害系を実証 |

各受け入れ条件は、単体・統合・障害注入テストに加え、実際のAWS認証・API操作を使用して検証する。

未証明の操作・機能・実行環境はリリース対象に含めない。
